# Content

Content is the editor-only publishing workspace in The Voyage. It uses the existing CRM type, colors, navigation and Muninn conversation. Both brands share the path from useful content to qualified conversations, with distinct audiences, positioning, channel ownership and campaign queues. WonPlace is credited to TideLine. Real sales conversations belong in Accounts with a contact and next step; followers and route checks are not leads or conversions.

The page reads `/api/content`. Each brand has one bounded snapshot in the existing D1 `documents` table (`content_snapshots`), so no migration is needed. No private campaign fixture, customer export, credentials or local filesystem paths are shipped in static assets. Actual captions and campaign evidence are imported after release from the existing publishing runtime. Media is identified by filename, dimensions, duration and hash; the CRM does not expose the Mac's filesystem or host the video. Local master files remain in the existing private content package.

`scripts/content-sync.mjs` reads the existing loopback publishing dashboard and explicitly exports a whitelist. `--send` signs each brand separately with the existing company-operations key from the existing mode-0600 `COMPANY_OPERATIONS_CONFIG`. The scoped `/api/content-source/:brand` route checks HMAC, method, path, timestamp and brand, then rejects outdated exports and prevents an older snapshot from replacing a newer one. There is no unsigned ingestion, arbitrary proxy, new credential vault or publishing command. The native publishing worker and its approvals, source verification, reservations and reconciliation remain authoritative. The snapshot synchronizer has no write access to that queue.

The managed release installs `com.tideline.voyage-content-sync` at five-minute intervals, copying reviewed modules into `~/Library/Application Support/TideLine/Voyage Content`. It reuses the existing private configuration by path, not a new key copy. It can be stopped with `launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/com.tideline.voyage-content-sync.plist`; this does not stop publishing. Snapshot age over 15 minutes is shown as stale. Refresh reads saved D1 evidence, not the local Mac directly. The private `sync-error.log` records failed imports; absence of a snapshot is explicitly unavailable. Performance is not measured until an actual source is integrated.

LinkedIn is the source, counted among the six platforms and never duplicated into itself. Scheduled source posts and verified published sources are distinct. Each destination retains its own queue state, blockers, caption, asset identity and actual published URL if present. Ready route checks never imply a post was published. General TideLine posts remain separate and held where brand destinations are unconfigured.

Ask Muninn opens the existing read-only chat with a brand/campaign-specific question. The Worker supplies current saved Content evidence, checked times, staleness and a bounded CRM excerpt via `/api/muninn/context?scope=content`; guests cannot see the internal marketing context. Each member still needs their existing local Codex connector. Muninn can explain and draft; it cannot publish, edit a queue or send outreach. Context stays within the existing bridge's 70,000-character bound.

Validation: `npm run check`; `node scripts/preview-content.mjs` provides a loopback-only review using the actual local publishing snapshot with no publish controls. Protected PR review precedes managed release. `scripts/release-content.mjs` pins the provider revision, imports both brand snapshots, installs sync and requires authenticated Content/filters/campaign/Muninn/responsive UI acceptance before a live completion receipt. Do not mark live completion from a homepage 200 or a unit test.
