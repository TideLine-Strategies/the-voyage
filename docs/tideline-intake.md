# TideLine leads and conversion analytics

This replaces the conflicting implementation in PR #11 on current main. The existing Company metrics cockpit and other brands remain intact. Editors open Profile → Admin → TideLine leads for the website inquiry/waitlist inbox, observed anonymous conversion counts, source-sync state, retry controls, and linked all-time CRM pipeline. Reads are on demand; no new polling is introduced. Phone waitlist consent is explicitly launch-only. This feature does not send messages.

The website deploy owns `tideline-contact` migration `0008_intake_conversions.sql`. It writes contacts/accounts/notes plus `tideline_links` into the existing Voyage database and records private sync receipts separately. The original inquiry and waitlist records are durable retry sources; a bounded ten-minute website cron reconciles pending entries. Ambiguous identity matches require editor review. Existing CRM account/contact fields and stages are not overwritten.

Voyage reuses the exact website `intake.js` module as `src/tideline-intake.js` for manual retries, with bindings `{CONTACT_DB: TIDELINE_DB, CRM_DB: DB}`. Keep the modules identical when modifying intake rules. The website counterpart is in the portfolio repository under `cloudflare/go/src/intake.js`. New normalized email identities share canonical IDs with saved Ask Loki contacts. Only exact already-normalized phone matches are reused; legacy formatting and ambiguous cross-identity matches may need manual reconciliation.

`GET /api/tideline/analytics` and `POST /api/tideline/import` require an active editor. POST also requires the same Origin. The public router’s session and role checks remain in force. The new source schema is detected: missing conversion tables return an explicit unavailable measurement rather than fabricated zeroes. Displayed lead rows are bounded to 200 per source and the chosen 7/30/90-day period. Linked pipeline is all time. Contract value is not received revenue.

Conversion events are server-side receipts for successful audit starts, saved conversations, contact inquiries and waitlist signups, deduplicated by an opaque source hash. Only anonymous session UUID, device class, kind and time are retained. DNT/GPC excludes events, and browser context contains no identity. The API returns aggregate counts, never anonymous session IDs or raw conversations. Contact/waitlist are alternative paths, so these counts are not a linear funnel or an identified browsing history. Existing retained audit statistics do not recover deleted historical audits.

Validation: 77 unit tests, actual-workerd auth/source tests, and `scripts/verify-tideline-runtime.mjs` with real D1 bindings prove duplicate-safe CRM linking and private summary reads without outbound messages. Browser fixture acceptance covers desktop/mobile inbox, conversion labels and retry success; the mobile grid column can shrink to the viewport. Website-side production acceptance tests its own CRM and all four conversion writes and removes only synthetic records without sending email/SMS.

Release uses protected independent review and the managed coordinator. `scripts/verify-tideline-release.py` verifies the exact deployed assets and anonymous denial; a real signed-in Profile → Admin → TideLine leads check must be performed after deployment before calling the UI live-verified. No new credentials or database migration is needed in Voyage. Use the existing Cloudflare default profile and account; do not change DNS or existing authentication.
